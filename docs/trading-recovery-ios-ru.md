# Никите (sxibaev): BUY, SELL и REDEEM после потери ответа

Контракт ветки `develop`. Перед включением новой логики для Polymarket убедись, что маршрут доступен в нужном окружении. Если старый API отвечает 404 на сам маршрут, это не результат ордера. Торговая попытка, операция пополнения и выплата — три разные сущности.

## Polymarket: обычные BUY и SELL (FOK)

До POST сохрани локально ключ попытки для текущего пользователя, контроллера, maker, токена и стороны. Это **EIP-712 digest самого подписанного Order в исходном домене биржи** (chain ID, exchange, версия домена), не подпись, tx hash, обёртка Deposit Wallet и не случайный идентификатор запроса. При потере ответа или возвращении на экран проверь оригинал: `GET /trade/polymarket/order-attempts/{orderHash}` с той же авторизацией и исходным выбранным кошельком (`x-hunch-wallet`). Этот маршрут не подписывает и не отправляет ордер.

Например, закрытая продажа, по которой биржа не указала исполненный объём: `{ "ok":true, "orderHash":"0x…", "orderId":"0x…", "state":"closed_unknown", "nextAction":"new_review" }` (хеши здесь сокращены). Успех HTTP означает, что запрос статуса обработан, а не что продажа исполнилась.

| state | nextAction | Что это значит |
|---|---|---|
| `unknown` | `check_original` | Нет доказанного итога. Дать закрыть экран и проверить исходный хеш позже. Не повторять POST. |
| `accepted` | `check_original` | Биржа приняла ордер; завершённое исполнение пока не подтверждено. Не показывать ошибку или завершённую сделку. |
| `filled` | `show_result` | Есть подтверждение исполнения. Обновить позицию, остаток и историю. Объём брать из данных сделки, не из исходного желания пользователя. |
| `not_submitted`, `no_fill` | `new_review` | Зафиксирован отказ до отправки либо доказано отсутствие исполнения. Новая сделка требует новой котировки и явного подтверждения. |
| `closed_unknown` | `new_review` | Биржа подтвердила закрытие точного ордера, но прошлый объём нельзя установить. Сохрани эту пометку; это не `no_fill`. Для нового SELL перечитай **продаваемые** доли этого владельца и исхода за вычетом открытых ордеров, для BUY — доступные средства с комиссиями и резервами. Начни с пустого объёма, не переноси подпись. При нуле покажи остаток. |

Один ответ биржи `not_found`, пустая история, таймаут и перезапуск приложения не дают разрешения повторить попытку. Нужна пара полей из API, привязанная к оригинальному хешу. Отсутствие результата одной сделки не должно блокировать весь кошелёк. Для funded BUY, Copy и Telegram остаются их собственные механизмы: этот POST-контракт не заменяет их.

Для нового Review сохрани исходный `assetContext` из котировки и адрес maker. Числовой `tokenId` может совпасть у двух разных контрактов долей. При SELL передай этот контекст в `POST /trade/polymarket/quote` с `includeSellAvailability: true`: проверь возвращённый `assetContext`, `sellAvailability.funderAddress` и возьми `sellAvailability.availableSharesRaw`. При прямом BUY передай тот же контекст и `funderAddress` в `POST /trade/polymarket/max-spend` (FOK, не `fundingScope: account`). Сверь контекст и funder; `maxAmountUsdRaw` — максимальная сумма самой покупки с учётом комиссий, `executableFundsRaw` — доступные средства. Ответ без проверяемой привязки или отсутствие поля — не нулевой остаток и не разрешение отправлять.

## Limitless: COLLATERAL CLOB FOK

- Прямой BUY или SELL: до POST сохранить `hunch-direct-<первые 32 hex-символа struct hash без 0x>`. В отличие от Polymarket это **хеш структуры**, без домена. Читать `GET /trade/limitless/orders/{recoveryId}` с исходным кошельком.
- BUY с пополнением: сохранить исходный `reservationId` и полный struct hash с `0x` до POST. Если ответ потерян, читать `GET /trade/limitless/orders/funded-recovery/{reservationId}/{orderStructHash}`; полученный `hunch-funded-…` использовать в том же GET статуса. Пополнение `ready` ещё не означает покупку.
- Явный `DELAYED` с подтверждением приёма — ордер принят и проверяется. Не показывать как ошибку. `missing`/пустой ключ не доказывают отказ даже после таймера. `filled`, `no_fill`, `failed` — исходы конкретной отслеженной попытки; не посылать заново старую подпись. У legacy, GTC и AMM другой путь.

## REDEEM: обе площадки

В основном API сохраняй `operationId`. После перезапуска читай `GET /position-actions/{id}`; явный Check status может вызвать `POST /position-actions/{id}/reconcile` для **той же** операции. Не вызывай заново prepare/claim/broadcast из-за таймаута.

- На Limitless/Base в поддерживаемой CTF-позиции `confirmationStage: payout_seen_awaiting_finality` означает, что выплата уже наблюдалась. Можно закрыть экран; `receiptStatus: pending` здесь не означает «выплаты нет». `checking_in_background` само по себе не подтверждает выплату.
- Polymarket не обязан возвращать промежуточную стадию выплаты. Для обеих площадок окончательный успех — `operation.status: completed`. Обнови позицию и баланс. Нулевой остаток позиции и рост общего баланса не заменяют данные конкретной операции.
- Если клиент поддерживает старый путь без `operationId`, сохраняй исходную сеть и ссылку на транзакцию/relay. Не переключай незавершённый redeem на другой способ отправки. Полученная квитанция транзакции не всегда означает окончательную выплату: в частности, внешний успех транзакции Safe не подтверждает успех внутреннего вызова.
